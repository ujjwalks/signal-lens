# Open red-team findings

From the catalogue review pass, 2026-08-01. The 4 blockers were fixed in 78c8030; these remain.

## Serious (25)

### f09.delivery_preparation :: legal.gpc_survivable

**Fails:** legal.gpc_survivable is true, but the entry's own terms_note says the opposite in plain words: "The order record is first-party transactional data and survives an opt-out signal because it is not tracking. The pre-purchase serviceability checker in rung 4 is the exception: it is on-device, it fires for unauthenticated visitors, and it does not survive an opt-out." legal.terminal_equipment_access is correctly true for that rung. Because the legal block is consumed as a pre-scoring boolean gate rather than a weighted penalty, gpc_survivable:true tells the gate the whole row - rung 4 included - survives an asserted Global Privacy Control, which is precisely the case the prose exempts. Rung 4 is also the only rung that fires pre-purchase, so it is the rung most likely to be built for acquisition.

**Fix:** Set legal.gpc_survivable to false, so the boolean matches the worst rung on the row and the gate errs safe. Keep the terms_note text unchanged - it already carries the nuance that the boolean cannot express - and add to it: "the legal facet is set to the rung-4 position because a single boolean cannot be true for one rung and false for another."

### f09.implementation_preparation :: legal.gpc_survivable

**Fails:** Identical self-contradiction to f09.delivery_preparation. legal.gpc_survivable is true while the entry's terms_note reads: "The documentation-pageview rung is different: it is on-device tracking of an unauthenticated visitor, it does not survive an opt-out signal, and it is exactly the surface behind the current wave of behavioural-telemetry claims. Treat the two rungs as having different permission positions even though they feed one row." The entry explicitly recognises that the row spans two permission positions and then encodes only the permissive one in the boolean the gate reads. legal.terminal_equipment_access is true and legal.cipa_exposure is "low" - both consistent with the docs-pageview rung existing - so the gpc value is the outlier, not a deliberate scoping decision.

**Fix:** Set legal.gpc_survivable to false. If the intent is to keep the backend-event rungs scored as opt-out-surviving, split the row: the server-side state-change events (rung 2) are a different acquisition path from the documentation pageview (rung 1's second half) and can carry terminal_equipment_access:false and gpc_survivable:true honestly. Do not leave one boolean covering two contradictory positions.

### f05.eligibility_check :: permission_requirement

**Fails:** permission_requirement is "notice" while rung 3 is "Verify declared facts against an authoritative register the subject has authorised you to query - a public licence or company register, or a regulated bureau check where one applies", requiring "a lawful basis and, for bureau checks, a permissible purpose". A consumer-credit bureau check is a consumer report under FCRA 15 U.S.C. 1681b(a), which is exhaustive ("under the following circumstances and no other") and carries adverse-action notice and dispute-rights duties; the equivalent regimes elsewhere impose comparable ones. The entry's access_conditions state this correctly - "Rung 3 changes the permission axis, not the availability axis" - and its terms_note states it again, but the machine-readable facet the pre-scoring gate reads still says "notice". f08.identity_verification, a comparable regulated step, correctly carries "regulated_access", so the catalogue has the right value available and does not use it here. legal.special_category_risk is additionally true on this row, which makes "notice" doubly wrong: if Art 9 data is genuinely in scope, notice is never a sufficient basis.

**Fix:** Set permission_requirement to "regulated_access" so the entry-level facet reflects the highest rung, matching f08.identity_verification. Then add a per-rung note in rungs 1 and 2's "gives" text: "needs notice only - this is a declared-facts gate with no external query". If the preference is to keep the row at "notice", delete rung 3's bureau clause entirely and leave only the register lookup, and say in access_conditions that bureau-backed affordability is a separate signal this catalogue does not carry.

### f11.subscription_renewal_window :: permission_requirement

**Fails:** permission_requirement is "none" while legal.person_level_resolution is true and the entry's own terms_note contradicts the facet twice: "using the same date to cross-sell something else is a secondary purpose and needs the notice to cover it", and "in several jurisdictions acting on the window is mandatory rather than optional: California's amended automatic-renewal law, in force from 1 July 2025, requires an annual reminder in the medium the customer is used to". A B2C subscription renewal date is personal data about an identified natural person, and the row's primary use case is contacting them. "none" is the enum floor and reads as "no permission facet applies", which is the availability position (you already hold the record) doing the permission axis's job - the specific inversion the contract forbids. Rung 4 additionally reads public procurement award registers, which carry their own reuse terms the facet does not signal.

**Fix:** Set permission_requirement to "notice". The record being your own contract data is an availability fact (availability is already correctly "available_now"); it is not a statement that no permission facet applies. Leave the terms_note as written - it is the best prose in the shard on this distinction - and add one sentence: "permission_requirement is set to notice because the row's activation is contact with an identified person, not because the record is hard to obtain."

### f08.account_verification :: permission_requirement

**Fails:** permission_requirement is "none" while legal.person_level_resolution is true, required_raw_fields include subject_id, and the row records email-address and phone-number verification transitions for named individuals. The entry's own access_conditions acknowledge the data's character - "Authentication logs are security records... the log... carries IP addresses and device data you do not need for this signal and should not retain for this purpose" - and note that seat and membership data is governed by the contract with the customer organisation. Structurally identical own-service rows carry "notice": f07.trial ("Using in-product behaviour to drive sales outreach is a secondary purpose. It must appear in the notice the trial user accepted") and f08.billing_setup, both about the seller's own records about its own users. "none" here again encodes "we already have it" - an availability fact - into the permission axis.

**Fix:** Set permission_requirement to "notice", matching f07.trial and f08.billing_setup. Add to access_conditions: "Verification events are generated for a security purpose. Reading them as a commercial readiness signal is a secondary purpose and has to appear in the notice the account holder accepted - the fact that your own auth system produced the event is an availability fact, not a permission."

### f02.website_browsing :: permission_requirement

**Fails:** permission_requirement is "notice" with legal.terminal_equipment_access true, and rung 3 reads "Stitch sessions to a persistent same-origin first-party identifier so browsing depth accumulates across weeks" requiring "a server-set identifier on your own origin". The sibling entry f02.device_and_session_continuity describes the identical mechanism at rung 1 - "Set the visitor identifier from your own server on your own origin rather than from a script" - and carries permission_requirement "explicit_consent". Two rows in one shard, the same act on the same device, two different permission values. Under ePrivacy Art 5(3) and PECR reg 6 the storing of, or access to, information on terminal equipment requires consent unless strictly necessary for a service the subscriber explicitly requested; a persistent analytics identifier is not strictly necessary on the EDPB's reading. This is systemic, not local: 25 of the 36 rows with terminal_equipment_access true carry "notice", and all 25 have jurisdiction_blocklist: [], so no field anywhere in the catalogue records that the EEA/UK position differs. A reader in Dublin or London filtering on permission_requirement gets a clean pass on a consent-requiring collection.

**Fix:** Two options, and the catalogue should pick one and apply it to all 25 rows. Either (a) set permission_requirement to "explicit_consent" wherever terminal_equipment_access is true, matching f02.device_and_session_continuity, and note in each entry that a notice-only position is the US default; or (b) keep "notice" as the US-default value and add "EEA", "UK" to legal.jurisdiction_blocklist on every terminal_equipment_access:true row, so the blocklist carries the divergence the single-value permission facet cannot. Option (b) is cheaper and truer to the existing enum. Whichever is chosen, add a line to README's design commitments: "terminal_equipment_access true means the EEA/UK permission position is consent regardless of what permission_requirement says, because permission_requirement carries one value and jurisdictions do not agree."

### f03.content_consumption :: access_conditions

**Fails:** Rung 1 instructs "Tag every content asset with a topic and a buying stage" and rung 3 "Attach consumption to a declared identity at the point content is gated... and backfill the prior anonymous history onto it", producing a per-person topic history. The entry carries sensitivity "low", legal.special_category_risk false, and no carve-out of any kind for sensitive topic taxonomies. Its nearest neighbour, f02.search_query, carries exactly the carve-out that is missing here: "Query text is free text and will occasionally contain special-category terms; matching it to a commercial lexicon is in scope, deriving a health, life-event or household attribute from it is not, and that class is documented as a prohibition with no implementation path." For a health, fertility, addiction-recovery, financial-hardship, immigration or legal-services publisher, a per-person topic history IS a derived health or sensitive attribute: WA MHMD RCW 19.373 defines consumer health data to include data "derived or extrapolated from nonhealth information... by any means, including algorithms", and the FTC's GoodRx, Premom and Flo Health actions - all three cited in restricted.health_status_inference - concerned precisely the assembly of audience segments from content and behaviour on those surfaces. The catalogue prohibits the inference in restricted.health_status_inference and then ships the instrumentation for it here with no adjacency note.

**Fix:** Add an access_condition mirroring f02.search_query: "The topic taxonomy is the risk, not the pageview. Where an asset's topic would itself disclose a health condition, a life event, a financial difficulty, an immigration or legal situation, or a protected characteristic, the topic must not be written onto a person's record - tag the asset at a commercial stage only and drop the topic. A per-person topic history over a sensitive taxonomy is a derived special-category attribute, and that class is documented at restricted.health_status_inference with no implementation path." Add "industry_exclude" entries or raise sensitivity to "medium" for the publisher case.

### f07.consultation :: legal.special_category_risk

**Fails:** legal.special_category_risk is true while sensitivity is "medium" and permission_requirement is "notice". Those three values cannot all be right. If Art 9 data is genuinely in scope, notice is never a sufficient basis - Art 9(1) is a prohibition lifted only by an Art 9(2) condition, of which explicit consent is the only one a commercial consultation can reach. The entry's own access_conditions confirm the data is really there: "Consultation notes are the most common route by which special-category detail enters a CRM as free text - a home survey records who lives there and how they live" and "A site visit puts your staff in someone's home or premises; the record of that visit carries obligations that a web event does not". Two other rows carry the same incoherent triple (f05.measurement_taken, f05.eligibility_check), while the two rows that resolve it correctly do so in opposite directions - f07.consent_and_access_granting at explicit_consent and f12.declared_care_episode_scheduling at regulated_access. So special_category_risk is currently doing two incompatible jobs across the catalogue: "this row processes Art 9 data" on some entries and "Art 9 data is adjacent and must be kept out" on others, with nothing in the data distinguishing them.

**Fix:** Decide which job the flag does and say so in README, then make this row consistent. The correct reading for f07.consultation is the second: the design excludes special-category content ("Score the structured outcome fields and keep raw note text out of the scoring and audience path entirely"), so set legal.special_category_risk to false and add an access_condition that states the adjacency in prose instead: "Special-category detail reliably enters the free-text note and must never reach the scored fields - the flag on this row is false because the scored schema excludes it, not because a home survey is neutral." If instead the intent is that Art 9 data is in scope, raise permission_requirement to "explicit_consent" and sensitivity to "high".

### f06.budget_allocation :: legal.person_level_resolution

**Fails:** legal.person_level_resolution is false while optional_supporting_fields contains declared_by_subject_id and budget_owner_role, and required_raw_fields is account_id_or_subject_id - a field that explicitly permits a person identifier. Rung 1 stores a budget figure a named individual stated on a qualification call; rung 3 stores a declared fiscal-year end against that person's account. A CRM opportunity carrying declared_by_subject_id resolves a natural person by construction. Compounding it, permission_requirement is "none" on a row whose access_conditions say "A budget figure a buyer states in confidence is commercial information about their organisation" - which is a confidentiality statement, not a reason for the permission facet to be empty. This row is otherwise the best statement of the orthogonality rule in the whole catalogue ("'public_cost_free' describes the price of the data, never the clearance to use it"), which makes the two facets below it more surprising, not less.

**Fix:** Set legal.person_level_resolution to true. Set permission_requirement to "notice" - a declaration made by a named individual in a sales conversation is personal data held under the seller's own notice, and "none" reads as "no permission facet applies". If the intent is genuinely account-only resolution, remove declared_by_subject_id from optional_supporting_fields and change required_raw_fields to account_id alone, so the schema matches the claim.

### f02.search_query :: legal.person_level_resolution

**Fails:** legal.person_level_resolution is false while required_raw_fields are subject_id, query_text and timestamp - raw free-text query strings stored against a subject identifier. Site-search boxes routinely receive the searcher's own name, email address, order reference, postcode and phone number, because people paste them in looking for their order; that is direct identification, not pseudonymous behaviour. The entry itself concedes the free-text hazard - "Query text is free text and will occasionally contain special-category terms" - and carries legal.cipa_exposure "high", the highest in the catalogue alongside f06.price_sensitivity. Rung 3 then persists a paid-search click identifier onto the session record, and click identifiers are re-identifiable within the ad platform's own measurement. Because the legal block is a pre-scoring boolean gate, person_level_resolution:false exempts the highest-CIPA-exposure row in the catalogue from every person-level check downstream.

**Fix:** Set legal.person_level_resolution to true. Add an access_condition: "A site-search log is a free-text field a person typed into. It regularly contains their own name, email, order reference or address, which makes the log person-level regardless of whether the session is authenticated - treat it as identified data, redact identifier-shaped tokens on write, and never ship the raw string into an analytics or audience store." Keep identity_level as "visitor" - that facet is about the resolution the signal is scored at, and it is correct; person_level_resolution is about whether a natural person is reachable in the record, and that is what is wrong.

### f15.weather_trigger :: permission_requirement

**Fails:** availability is public_cost_free and permission_requirement is "none", but rung 4 - described as "the rung where this becomes revenue rather than a chart" - is "an outbound message to existing customers at affected addresses whose asset or last service makes them exposed", requiring "an address-level customer or installed-base record". That is direct marketing to identified individuals selected on a joined attribute, and the entry's own terms_note says so: "the customer address you join it to sits under whatever basis you already hold it for, and using it for outbound marketing is governed by direct-marketing rules that are independent of the weather feed's terms". The permission facet describes the weather API (free, no permission needed) and silently inherits that clearance for the customer join, which is the availability-eats-permission inversion in its clearest form: the weather data's zero cost is being read as the row's clearance. legal.person_level_resolution is also false on a row whose top rung selects and messages named customers.

**Fix:** Set permission_requirement to "notice" - the facet must describe the row's activation, not its cheapest input. Add an access_condition: "The meteorological feed needs no permission; the customer list you join it to needs whatever basis you already hold, and messaging a person because a condition was forecast at their address is direct marketing under rules the weather feed's terms say nothing about. Rungs 1 to 3 hold nothing personal and are genuinely permission-free; rung 4 is not, and the row's facet is set for rung 4." Consider setting legal.person_level_resolution true, or explicitly scoping rung 4 out of the row.

### f10.trade_in_activity :: access_conditions

**Fails:** Rung 1 captures "the declared model and year as the two highest-value fields on the form" - a declared statement of what the person owns - and optional_supporting_fields carries serial_or_registration and preferred_replacement_model. The entry carries no exclusion for medical, assistive, mobility or reproductive-health device classes; the strings "medical" and "assistive" appear nowhere in it. Its siblings f10.product_usage and f10.maintenance_and_failure both carry the exclusion explicitly, and restricted.medical_and_assistive_device_replacement_inference covers "resale, trade-in and disposal listings" by name and cites f10.trade_in_activity as one of the two rows the lawful declared variant is authored on. The declared basis makes the collection lawful; it does not make the retention lawful. A stored declared_model of a mobility scooter, hearing aid, CPAP or fertility device, held with quoted_value and offer_accepted_flag against a subject_id, is a disability or health attribute on a marketing record - GDPR Art 9 with no available condition, and WA MHMD consumer health data. The row's own false_positives even name "a device bought second-hand"-style confounds nowhere, so nothing in the entry warns the reader.

**Fix:** Add the sibling access_condition: "Exclude medical, assistive, mobility and reproductive-health device classes from the valuation catalogue. A declared model is a lawful basis to quote a trade-in and is not a lawful basis to retain a disability or health attribute - quote it, price it, and do not write the model class onto the customer profile or into any segment. See restricted.medical_and_assistive_device_replacement_inference." If the business genuinely trades in such devices, add a second condition requiring the model field to be dropped from the customer record on quote completion and excluded from every audience export.

### f09.onboarding_scheduling :: required_raw_fields

**Fails:** The definition states outright that absence 'qualifies as well, and is the more valuable half: a closed account with no kickoff booked N business days after close is a stalled onboarding.' Rung 1's own `requires` list asks for 'a list of closed accounts with close dates'. But `contract_close_date` is in optional_supporting_fields. With exactly account_id, event_type, scheduled_start and event_status you can enumerate bookings that exist and nothing else — you cannot compute days-from-close-to-kickoff, and you cannot produce the null that the whole signal turns on. Simulated: the rule 'list every closed account where days_close_to_kickoff is null after five working days' is unwritable with the required set.

**Fix:** Promote `contract_close_date` from optional_supporting_fields into required_raw_fields. Also add `account_status_or_close_state` so the row can tell a closed account from a prospect. Leave days_close_to_kickoff in optional — it is derived, not raw.

### f11.loyalty_programme_behaviour :: required_raw_fields

**Fails:** The qualifying condition names five triggers: balance at redemption threshold, benefit/points expiry inside the outreach window, tier qualification within reach with the qualifying period ending, a redemption started but not completed, and an accrual gap. Only the first and the last are computable from required_raw_fields (member_id, points_balance, accrual_event_date, programme_status). points_expiry_date, tier, tier_threshold_gap, qualifying_period_end and redemption_started_at are ALL in optional. Rung 1 — the this-week rung — explicitly instructs 'Export three columns from the programme ledger: balance, points expiry date and tier gap', so two of the three fields rung 1 names are not required fields of the row it belongs to.

**Fix:** Promote `points_expiry_date`, `tier_threshold_gap` and `qualifying_period_end` into required_raw_fields (they are columns any loyalty ledger already holds), and add `redemption_started_at` if the abandoned-redemption trigger is to stay in the qualifying condition. Alternatively narrow the qualifying condition to the balance-threshold and accrual-gap cases and move the rest to a note — but do not leave five triggers advertised and two buildable.

### f10.lifecycle_stage :: required_raw_fields

**Fails:** The qualifying condition is a genuine OR: 'asset age at or beyond the category's median replacement interval, OR a dated end-of-support, warranty-end or lease-end event inside the review horizon.' required_raw_fields (asset_id_or_serial, owner_account_id, service_start_date, category_replacement_interval_months) supports only the first branch. warranty_end_date, service_contract_end_date, end_of_support_date and lease_end_date are all in optional_supporting_fields. So the second branch — which is the higher-precision half, because a published end-of-support date is a fact rather than a median — is undetectable from the required set. Rung 2 is entirely about that branch ('Publish your own end-of-support, end-of-life and last-order dates per model').

**Fix:** Add a required alternative rather than four more mandatory columns: make required_raw_fields ['asset_id_or_serial','owner_account_id','service_start_date_or_dated_end_event','dated_end_event_type','category_replacement_interval_months'] and record in min_data that one of service_start_date or a dated end event must be present. That keeps the row buildable for a seller who has only install dates and for one who has only an EOL calendar.

### f03.social_proof_momentum :: required_raw_fields

**Fails:** The definition has two halves — referral sessions accelerating against a source baseline, and 'the public proof itself accelerates, in review postings, ratings, followers or stars, against the baseline you have been recording' — and the qualifying condition says 'at least one session OR PROOF EVENT falls inside the burst window'. required_raw_fields is source_id, session_id, timestamp: there is no count field of any kind, so the second half is undetectable. review_posting_count, public_proof_count_series and mention_count are all in optional. Rung 3 ('Snapshot the public proof counts that move without producing clicks') produces no session_id at all and therefore emits nothing the required set can hold. The row's own access_conditions concede that 'a baseline you did not capture cannot be reconstructed later; the weekly snapshot is the whole of rung 3' — so the entry knows the branch matters and still leaves its field optional.

**Fix:** Add `proof_count_value` and `proof_count_type` to required_raw_fields and make session_id conditional ('session_id for the referral branch, proof_count_value for the public-proof branch — one or the other'). State the either/or in min_data alongside the existing baseline_weeks and min_sessions floors.

### f03.community_recommendation :: required_raw_fields

**Fails:** identity_level is `individual`, but required_raw_fields is post_id, community_id, post_text, timestamp — there is no actor identifier at all. `author_handle` sits in optional_supporting_fields. With exactly the required fields the row resolves to a post, not to a person, so it cannot be deduplicated by author, cannot support the min_data rule about repeat posters, and cannot be joined to anything at individual level. The sibling row f03.social_engagement gets this right and requires `actor_handle`. As authored, the identity_level claim is unbacked by the fields, which is precisely the failure the baseline study measured (0/7 runs assigned an identity level) reappearing as an identity level that the fields cannot deliver.

**Fix:** Promote `author_handle` into required_raw_fields, keeping the existing access_condition that a community handle is a pseudonym and resolving it to a person is a separate act with its own basis. If the row is meant to be a read-this-lead artefact rather than a person, change identity_level to `visitor` and say so in the definition — but do not claim individual identity from four fields that contain no actor.

### f14.buying_group_formation :: required_raw_fields

**Fails:** The qualifying condition requires that two distinct people 'touch the same opportunity, artefact or product instance within the window'. required_raw_fields is account_id, person_id, interaction_event, timestamp — no opportunity or artefact key. opportunity_id and shared_artefact_id are both optional. The entry contradicts itself: min_data's own note says 'a domain with hundreds of unrelated users is a large organisation, not a buying group, and needs an opportunity or artefact key to be meaningful'. So the row states the required key in its threshold note and then does not require it, and rung 1 (count distinct people per email domain) will fire on every enterprise with more than one signup.

**Fix:** Promote a single field `opportunity_or_shared_artefact_id` into required_raw_fields. Keep rung 1 as the domain-count starting point but re-label what it gives as 'a candidate list that needs an opportunity or artefact key before it is a buying group', matching the language already in min_data.

### f12.education_enrolment_cycle :: capability_ladder[0]

**Fails:** Rung 1 is 'Aggregate your own order dates by week for the last two years and read off the seasonal shape your customers already have... without knowing anything about any individual.' That satisfies neither branch of the qualifying condition (an enrolment fact supplied by the student or parent, OR a published institutional calendar joined to a declared location) and produces none of the four required_raw_fields — no subject_id, no declared stage, no term start date, no calendar_source_id. It is a useful demand-curve back-test but it is not this signal, and putting it at rung 1 makes the row look acquirable this week when the first rung that actually emits the signal is rung 2. min_data reinforces the error by defining `min_seasons_of_history_for_rung_1`.

**Fix:** Promote the current rung 2 (maintain a term/half-term/exam/results calendar table for the regions you serve and join it to the customer's declared region) to rung 1 — it is genuinely a week's work, needs only a declared country, and does emit calendar_source_id and term_or_course_start_date. Demote the order-date seasonality read to a prerequisite note under access_conditions ('calibrate your lead time against your own order curve before setting the trigger'), and rename the min_data key accordingly.

### f10.trade_in_activity :: capability_ladder

**Fails:** Every rung is a build, and rung 1 is the biggest: 'Put a valuation tool on your own site and instrument it end to end', requiring a valuation page and a price table that do not exist yet. Rung 2 adds the same tool to more flows, rung 3 needs a buyback partner contract, rung 4 needs listing-source monitoring. There is no rung that reads records the company already holds — yet trade-in intent already arrives today in support tickets and sales notes ('what's my old one worth?'), in returns and RMA records that already carry model and condition, and in upgrade enquiries in the CRM. This is the one ladder in the catalogue with no zero-build rung, which is the exact failure mode the contract names.

**Fix:** Insert a new rung 1: 'Classify the trade-in and buyback enquiries you already receive — search the last twelve months of helpdesk tickets, CRM notes and returns records for valuation, buyback, part-exchange and upgrade language, and extract the model named in each. requires: helpdesk and CRM text export. gives: a declared-model trade-in cohort from records that already exist.' Demote the valuation tool to rung 2 and renumber. That also makes the availability value (website_instrumentation) true of rung 2 rather than of the whole row.

### f07.consultation :: availability

**Fails:** availability is `integration`, but the row's own rung 1 says 'separating those two populations needs no integration at all - a checkbox in the diary or CRM will do it', requiring only 'the diary or CRM your team already books into'. Since availability is defined in the validator as the cost/effort axis and the capability ladder exists to say what is possible today, setting availability from the top rung inverts the field's meaning and hides the row from any downstream available_now filter. This is systemic, not isolated: f07.time_investment_escalation is `integration` while its rung 1 says 'The comparison is the work; the data is already there'; f09.implementation_preparation is `integration` while its rung 1 says 'Both exports exist today in the helpdesk and the web log'; f07.seller_inventory_allocation is `integration` for one weekly export from systems you already run; f02.channel_switching is `integration` for putting your own id on your own outbound links; f15.supply_disruption is `partial` for a join across your own order, service and warranty exports.

**Fix:** Set availability from RUNG 1, not from the ladder's ceiling, and say so in the field's contract note. f07.consultation, f07.time_investment_escalation, f09.implementation_preparation and f15.supply_disruption become `available_now`; f07.seller_inventory_allocation becomes `available_now`; f02.channel_switching becomes `website_instrumentation`. Where a higher rung genuinely changes the axis, record that in access_conditions the way f10.lifecycle_stage already does for its rung 4 ('the permission requirement for that rung is regulated access and it does not inherit this entry's clearance').

### f11.subscription_renewal_window :: required_raw_fields

**Fails:** The qualifying condition is an explicit formula — 'today within [term_end - notice_period - lead_time, term_end]' — but `notice_period_days` is in optional_supporting_fields. required_raw_fields is account_id, subscription_status, term_end_date, auto_renew_flag. Rung 3 exists specifically to capture notice ('when does your current agreement end, and what notice does it need?'), which confirms the field is not decorative. Built from the required set alone, the window opens at the wrong date for every contract carrying a notice period — commonly 30, 60 or 90 days — and the row silently fires after the cancellation deadline has already passed on exactly the accounts it matters most for. This is the catalogue's flagship 5/5 row, so the error propagates.

**Fix:** Promote `notice_period_days` into required_raw_fields. If a seller genuinely has no notice column, record a default in min_data and label it honestly — e.g. 'notice_period_days defaults to 0 where the contract term is not machine-readable; a 0 default means the row fires late for any account whose contract requires notice, and that is a data-entry gap, not a modelling choice' — mirroring the wording f13.capacity_pressure already uses for entitlements trapped in PDFs.

### f11.replenishment_due :: required_raw_fields

**Fails:** The qualifying condition has two branches: 'at least two prior purchases of the same consumable, OR one purchase plus a declared usage rate or a manufacturer-stated service interval'. required_raw_fields is subject_id, item_id, order_date, quantity — `pack_size` and `declared_usage_rate` are both optional, so the second branch is undetectable and the first cannot be converted into a depletion DATE (quantity without pack size gives orders-per-year, not units-per-day). Rung 2 depends on exactly those two fields ('pack size and dose or units-per-use on the product record'), and it is the rung that covers first-time buyers. The sibling row f12.household_consumption_rate performs the same computation and correctly requires pack_size — so the catalogue contradicts itself between two rows that reference each other in their own definitions.

### f14.household_coordination :: required_raw_fields
